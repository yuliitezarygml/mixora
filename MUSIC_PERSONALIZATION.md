## Реализованный сценарий Mixora

1. После входа читается аккаунтный профиль интересов. Если настройка ещё не
   завершена, поверх обычного приложения открывается окно в стиле авторизации.
2. Пользователь выбирает минимум пять разных артистов, до 30, и любые из
   12 поддерживаемых жанров. Артистов можно искать в существующих SoundCloud
   и Spotify API. Это поиск предпочтений, не ограничение источников музыки.
3. «Настроить Мою волну» сохраняет профиль на сервере и продолжает отложенный
   запуск волны. «Пропустить пока» сохраняет осознанный отказ от настройки.
   Простое закрытие окна не отмечает её выполненной: при следующем входе она
   будет предложена снова. В настройках есть «Музыкальные интересы».
4. Пока нет лайков и истории, запросы чередуют выбранных артистов/жанры.
   Ранжирование повышает подходящих кандидатов; до шести совпадающих треков
   получают cold-start приоритет перед popular fallback Gorse. Уже выбранная
   станция артиста/жанра не подменяется стартовым профилем.
5. Когда появляются настоящие лайки и история, они становятся основным
   контекстом; профиль остаётся слабым дополнительным сигналом. Существующие
   Gorse, text embeddings и rules fallback сохранены. Выбор артиста не создаёт
   фиктивные `like`/`play` события, provider IDs или собственный каталог песен.

## Контракт и хранение

Authenticated `GET /api/v1/me/taste` возвращает:

```json
{"artists": [], "genres": [], "completed": false}
```

Authenticated `PUT /api/v1/me/taste` принимает:

```json
{
  "artists": ["Tycho", "ODESZA", "Bonobo", "RAC", "Daft Punk"],
  "genres": ["electronic", "indie"],
  "skip": false
}
```

`{"skip": true}` сохраняет пустой завершённый профиль. Иначе сервер требует
пять уникальных имён, удаляет пробелы/дубликаты, проверяет ограничения и жанры.
`completed` определяется сервером, а не доверяется клиенту. Запрос ограничен
16 КБ. Миграция `014_user_taste_profiles.sql` создаёт `user_taste_profiles`
с внешним ключом на пользователя; профиль отделён от библиотеки и событий.

Смена аккаунта/выход отменяют загрузку. Поздний GET не может отменить успешный
PUT, поздний ответ другого аккаунта не может заменить текущий профиль.
Одновременные изменения на разных устройствах пока имеют last-write-wins,
не revision/merge протокол библиотечных плейлистов.

## Исправление foreground playback в Tauri

Раньше authenticated media возвращало явную заглушку: WebView не владеет
Rust cookie-сессией. Теперь Rust выдаёт opaque grant для строго одного пути
серверного media proxy, а loopback HTTP передаёт запрос с private session.
Cookie и signed CDN URL не становятся renderer credentials.

Backend ограничивает provider-ответы порциями по 1 МБ. Native мост собирает
полный запрошенный диапазон последовательным streaming: обычный GET получает
200/полную длину, Range получает 206/корректный Content-Range, HEAD не содержит
тела. Ограничения памяти, TTL, разрешённых методов и Host сохранены. Один
retry при 502/504 повторяет тот же Range, не перескакивает на другую песню.

Это foreground HTMLAudio/WebView, **не** фоновые Android Media3/iOS AVPlayer.
Недоступные, приватные, геоограниченные и удалённые provider-треки не могут
быть гарантированы этим мостом. Spotify по-прежнему только доступный preview;
VK/Bandcamp работают через существующий URL-based вход, не выдуманный поиск.

## Следующие проверки качества

- Пяти-source сценарий на физических Android/iPhone и подписанных сборках.
- Background/lock-screen, interruption/Bluetooth, secure session и native WS.
- Замер completion/early-skip, разнообразия артистов и источников, времени
  ответа и повторов; сравнение правил, Gorse и embeddings на реальных событиях.
- Управляемая exploration, artist aliases/collaborations и жанровые синонимы.
- Offline evaluation перед CLAP/audio embeddings: новая модель сама по себе
  не исправляет малый/неподходящий каталог или недоступный upstream.

Воспроизводимые проверки и текущие ограничения — `app-andorid-ios/QA.md`.
